## Rationale

The embedded constraint is "less RAM, less time, more predictability." The
language feature that helps most directly is `constexpr`: anything you can
compute at compile time costs no RAM, no init cycles, no WCET term, and
lands in `.rodata`, which on a typical microcontroller means flash. The
runtime sees only the result.

The mechanical wins are concrete:

- A 256-entry CRC table at runtime: 1 KiB of `.bss` + 256 multiplications
  at startup. At compile time: 1 KiB of `.rodata` and zero init.
- A protocol parser dispatch table built from a `consteval` function: lives
  in flash, with no construction order ambiguity (`LIFE.6`).
- A sine / cosine table for fixed-point DSP, generated by a `constexpr`
  function over a `constexpr std::array`: same story.

`consteval` (C++20) makes this a *requirement*, not a possibility. A
`consteval` function may only be called in constant-expression contexts;
if a refactor accidentally introduces a runtime path, the compiler refuses.
That is the embedded-relevant property: the regression that pushes work
back to runtime becomes a compile error rather than a silent code-size
and init-time regression.

## Guidance

- **Mark anything that *can* be computed at compile time `constexpr`.**
  CRC tables, sine / cosine tables, parser dispatch tables, command-ID
  maps, hardware-config lookup tables, fixed-point coefficient sets.
- **Mark functions whose results *must* be compile-time `consteval`**
  (C++20). The compiler enforces the requirement; an accidental runtime
  call becomes a build failure.
- **Generate tables with `constexpr` functions** that return
  `std::array<T, N>`. Initialise the array at namespace scope; it lands in
  `.rodata`.
- **Push configuration parsing to compile time** where the inputs are
  static. A `constexpr` parser over a `std::string_view` literal turns a
  textual configuration into a typed dispatch table at no runtime cost.
- **Audit startup time.** Anything that allocates or computes in
  `__libc_init_array` (C++ global construction) is a candidate for
  `constexpr` relocation.
- **Check `.rodata` vs `.bss` in the link map.** If a table you expect in
  flash is in RAM, something is not `constexpr` — the table got
  copy-on-startup'd because its initialiser is not a constant expression.

## Example

```cpp
// Bad: a CRC-32 table computed at startup. 256 multiplications and 1 KiB
// of RAM consumed before main() runs.
namespace bad {
    std::array<std::uint32_t, 256> crc_table;

    void init_crc_table() {
        for (std::uint32_t i = 0; i < 256; ++i) {
            std::uint32_t c = i;
            for (int k = 0; k < 8; ++k)
                c = (c & 1) ? (0xEDB88320u ^ (c >> 1)) : (c >> 1);
            crc_table[i] = c;
        }
    }
}

// Good: the same table, computed once by the compiler. Zero RAM cost;
// lives in .rodata; no startup penalty.
namespace good {
    consteval std::array<std::uint32_t, 256> make_crc_table() {
        std::array<std::uint32_t, 256> t{};
        for (std::uint32_t i = 0; i < 256; ++i) {
            std::uint32_t c = i;
            for (int k = 0; k < 8; ++k)
                c = (c & 1) ? (0xEDB88320u ^ (c >> 1)) : (c >> 1);
            t[i] = c;
        }
        return t;
    }

    inline constexpr auto crc_table = make_crc_table();   // .rodata
}

// consteval is the load-bearing word above. With consteval, a refactor
// that accidentally calls make_crc_table() at runtime is a compile error.
// With constexpr alone, the compiler is permitted to evaluate at runtime
// when the call appears in a non-constant context — the silent regression
// this guideline is meant to prevent.

// constexpr also extends to small parsers, useful for configuration.
constexpr std::uint8_t parse_hex_nibble(char c) {
    if (c >= '0' && c <= '9') return std::uint8_t(c - '0');
    if (c >= 'a' && c <= 'f') return std::uint8_t(c - 'a' + 10);
    if (c >= 'A' && c <= 'F') return std::uint8_t(c - 'A' + 10);
    return 0xFF;   // sentinel; constexpr functions can't throw
}

constexpr std::array<std::uint8_t, 4> parse_mac_prefix(std::string_view s) {
    return {
        std::uint8_t((parse_hex_nibble(s[0]) << 4) | parse_hex_nibble(s[1])),
        std::uint8_t((parse_hex_nibble(s[2]) << 4) | parse_hex_nibble(s[3])),
        std::uint8_t((parse_hex_nibble(s[4]) << 4) | parse_hex_nibble(s[5])),
        std::uint8_t((parse_hex_nibble(s[6]) << 4) | parse_hex_nibble(s[7])),
    };
}

inline constexpr auto vendor_oui = parse_mac_prefix("DE:AD:BE:EF");   // .rodata
```

## Caveats

- **Compile-time evaluation has limits.** Until C++20, `constexpr` could
  not use much of the standard library; C++20 added `constexpr std::vector`
  and `constexpr std::string` with the restriction that any allocation
  must be deallocated within the same constant evaluation. Lookup tables
  fit comfortably; do not try to keep heap state across the boundary.
- **Heavy `constexpr` work slows compilation.** A 4096-entry table
  generated by a non-trivial function compiles fine but adds seconds. Be
  willing to move very large tables to a build-time code generator if
  compile time bites.
- **`consteval` is C++20.** On older toolchains, `constexpr` with a
  call-site discipline (always assign to a `constexpr` variable) is the
  closest approximation.
- **Floating-point `constexpr` is conforming since C++23**, but toolchain
  support is uneven. Verify with the target toolchain before relying on
  a sine / cosine table generated by `constexpr` `<cmath>`.
- **Tables in flash still cost a load.** A `constexpr` table is free at
  startup but the runtime read still touches flash. For very hot tables,
  use `__attribute__((section(".dtcm")))` to place them in tightly-coupled
  memory — that is build-system territory beyond this guideline.
